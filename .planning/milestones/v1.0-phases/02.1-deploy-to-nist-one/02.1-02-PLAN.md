    Write `deploy/deploy.sh` (bash; executable in git). Shell setup:
    - `set -Eeuo pipefail`, never `-x`, `umask 022`.
    - Wrap the whole body in `main() { ... }; main "$@"; exit`, so a `git pull` that rewrites the script mid-run cannot corrupt bash's incremental read.

    Constants at the top, each with a one-line comment:
    - `APP_DIR=/srv/birja`. This is the prod checkout. The script never touches the dev tree at /home/YokaiExchange, wherever it is invoked from.
    - `ENV_FILE=/etc/birja/prod.env`, `WEB_ROOT=/var/www/birja`, `STATE_DIR=/var/lib/birja`, `DEPLOY_LOG=$STATE_DIR/deploys.log`, `LOCK=/var/lock/birja-deploy.lock`.
    - `HOST=birja.nist.one`, `CERT=/etc/nginx/certs/nist.one/fullchain.pem`, `NODE_IMAGE=node:24.22.1-trixie-slim`, `KEEP_RELEASES=3`.
    - `REF="${DEPLOY_REF:-main}"`.
    - A `dc` function: `docker compose -f "$APP_DIR/docker-compose.prod.yml" --env-file "$ENV_FILE" "$@"`.

    Arguments:
    - none: deploy `$REF`.
    - `--rollback`: see below.
    - `-h`/`--help`: print usage and exit 0 before any check. Usage covers the deploy command, DEPLOY_REF, --rollback, and the note that rollback does not undo migrations.
    - anything else: usage, exit 2.

    Preflight, in order; fail fast with a clear one-line message:
    1. Must run as root.
    2. Take `flock -n 9` on $LOCK via `exec 9>$LOCK`.
    3. $APP_DIR is a git checkout and `git -C $APP_DIR status --porcelain` is empty (refuse a dirty tree).
    4. $ENV_FILE exists, is owned by root and has mode 600 (`stat -c '%a %U'`).
    5. `grep -qE '^RESEND_API_KEY=.+'` and `grep -qE '^EMAIL_FROM=.+'` both match on the env file. Use `-q` only and never print the lines.
    6. $CERT exists. `openssl x509 -checkend 0` must pass (expired means fail). If `-checkend $((30*86400))` fails, print a renewal warning pointing to deploy/RUNBOOK.md.

    Deploy steps:
    1. `git -C $APP_DIR fetch --prune --tags origin`. Resolve the ref: try `origin/$REF^{commit}` first, then `$REF^{commit}` (tag or SHA). Run `git -C $APP_DIR checkout --detach <sha>` and print `Deploying <ref> = <short sha>`.
    2. Refuse if `backend/` or `docker-compose.prod.yml` is missing at that SHA (RESEARCH pitfall 1: `main` before the release has no app).
    3. `dc up -d --wait postgres redis`.
    4. `dc build backend`.
    5. Migrate once: `dc run --rm --no-deps backend alembic upgrade head`. A failure aborts here, before the running backend is replaced.
    6. `dc up -d --wait backend`.
    7. Frontend build: `docker run --rm -v "$APP_DIR/frontend":/app -w /app $NODE_IMAGE sh -c 'npm ci && npm run build'`.
    8. Release dir: `$WEB_ROOT/releases/<short-sha>-<UTC yyyymmddThhmmssZ>`. `install -d` it, copy `frontend/dist/.` into it with `cp -a`, then `chmod -R a+rX` so nginx (www-data) can read it.
    9. Atomic swap: `ln -sfn <rel> $WEB_ROOT/current.tmp && mv -Tf $WEB_ROOT/current.tmp $WEB_ROOT/current`.
    10. Run `$APP_DIR/deploy/install-nginx.sh` (plan 03).
    11. Health check, up to 15 tries 2 s apart:
        - `curl -fsS --resolve $HOST:443:127.0.0.1 https://$HOST/api/v1/health` returns JSON with `"status":"ok"` (parse with `python3 -I -c`; no jq).
        - `curl -fsS --resolve ... https://$HOST/` returns HTML containing `id="root"`.
    12. Append `<UTC ISO time> <full sha> <release dir> <ref>` to $DEPLOY_LOG (`install -d -m 755 $STATE_DIR` first).
    13. Prune old releases. Keep the newest $KEEP_RELEASES dirs, and never delete the current target or any dir referenced by the last two DEPLOY_LOG lines (`readlink -f $WEB_ROOT/current`).

    `--rollback`:
    - Read the second-to-last line of $DEPLOY_LOG. If there are fewer than 2 lines, print "nothing to roll back to" and exit 1.
    - Check out that SHA detached in $APP_DIR.
    - `dc build backend && dc up -d --wait backend`. Skip migrations, and print a warning that the schema stays at the newer revision; a schema-incompatible rollback needs a manual `alembic downgrade` and there are no backups until Phase 6 (RESEARCH section 7).
    - If that line's release dir still exists, swap `current` to it atomically. Otherwise rebuild the frontend as in steps 7-9.
    - Run the same health check, then append a log line with ref `rollback`.

    Failure handling: an ERR trap prints the failing step name and the last 50 backend log lines, redacted with `dc logs --no-color --tail 50 backend | sed -E 's/code=[0-9]{6}/code=******/g; s/to=[^ ]+/to=***/g'`. It then prints the rollback command `/srv/birja/deploy/deploy.sh --rollback`.

    Hard rules for the script: never print env values; never run unquiet `dc config`; never `docker inspect`; never `down -v`; never touch the dev compose project `birja` or /home/YokaiExchange.

    Undo, as a header comment:
    - `docker compose -p birja-prod down` stops the stack. Volumes are kept; `down -v` deletes all prod data, so only run it with explicit intent.
    - Then `rm -rf /srv/birja /var/www/birja /var/lib/birja`.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host loopback -> backend container | Only host processes (nginx) can reach 127.0.0.1:18000 |
| backend -> data network | Postgres/Redis reachable only from backend; network is internal (no internet) |
| GitHub origin -> /srv/birja checkout | Code deployed is whatever the ref resolves to |
| env file -> containers | Secrets cross into container env via compose interpolation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02.1-06 | Spoofing | uvicorn proxy headers | mitigate | `--forwarded-allow-ips` pinned to the prod app subnet 172.29.50.0/24 (never `*`); only nginx can reach the loopback port; verified at runtime in 02.1-06 |
| T-02.1-07 | Information disclosure | Postgres/Redis exposure | mitigate | No `ports:` on either; `data` network `internal: true`; Redis requirepass; checked by smoke (plan 04) |
| T-02.1-08 | Information disclosure | prod secrets | mitigate | init script writes 600 root file under 700 dir, never prints values; deploy.sh checks perms and presence with `grep -q` only; no `config`/`inspect`/`-x` |
| T-02.1-09 | Elevation of privilege | weak or placeholder secrets | mitigate | `openssl rand -hex 32` per secret; `${VAR:?}` rejects empty; app rejects `change-me*` and short secrets in prod |
| T-02.1-10 | Tampering | deploy of wrong/empty ref | mitigate | Resolves `origin/<ref>` first, prints SHA, refuses when `backend/` missing; dirty-tree refusal; flock prevents concurrent deploys |
| T-02.1-11 | Denial of service | failed migration or build mid-deploy | mitigate | Migrate before replacing backend; frontend swap is atomic after a successful build; ERR trap prints rollback command |
| T-02.1-12 | Repudiation | which version is live | mitigate | deploys.log records time, SHA, release dir, ref |
| T-02.1-13 | Tampering | containers running as root | mitigate | Backend runtime image is non-root uid 1001; `no-new-privileges` on all services |
| T-02.1-13a | Elevation of privilege / Information disclosure | Postgres app role is the image superuser (`POSTGRES_USER=birja`) and backend->Postgres has no SSL, against the CLAUDE.md Datastores rule (least-privilege role + SSL) | accept | Accepted for 02.1 only, with these compensating controls: the `data` network is `internal: true`, Postgres publishes no port, and the traffic never leaves this single host (backend and Postgres share the Docker bridge), so SSL would protect no network hop. Strong generated password, root-600 env file. Tracked as a Phase 6 success criterion in ROADMAP.md: a least-privilege app role, and a recorded DB SSL decision |
