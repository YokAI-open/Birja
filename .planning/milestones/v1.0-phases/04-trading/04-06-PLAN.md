<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated request -> trading service | user_id comes only from the session (CurrentUserDep), never from the body |
| concurrent requests -> same account row | many workers/connections can target one balance |
| prices table (scheduler) -> trade | external-sourced mid used for execution |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-19 | Tampering | double spend via parallel requests | mitigate | Account FOR UPDATE first, holding FOR UPDATE second, one transaction; CHECK backstops from 04-03; concurrency proof in 04-08 |
| T-04-20 | Tampering | replay / double submit | mitigate | Lookup under the account lock before any price check; UNIQUE backstop with IntegrityError -> replay path (tested by forced race) |
| T-04-21 | Tampering | client-chosen price | mitigate | Execution uses only prices.mid read in the transaction; expected_mid can only cause a refusal |
| T-04-22 | Tampering | trading on stale or missing prices | mitigate | freshness() == "fresh" required at quote and execute (D-03); no-price -> stale_price |
| T-04-23 | Information disclosure (IDOR) | other users' trades via a guessed key | mitigate | Every lookup filters by user_id; UNIQUE is (user_id, key) |
| T-04-24 | Denial of service | lock held on refusal | mitigate | Explicit rollback before raising; idle_in_transaction_session_timeout 30 s backstop (main.py) |
| T-04-25 | Information disclosure | logs | mitigate | Log trade id, user id, side only |
</threat_model>
