# Phase 02.1: Code Review Report

**Reviewed:** 2026-10-27T20:03:04Z
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

I reviewed the production deploy tooling (deploy, rollback, nginx install, Cloudflare real-IP, manual ACME renewal, smoke checks), the prod compose file, the nginx site, the CI changes and the `ENV`-required settings change. I also checked the live host read-only: `nginx -T`, `docker compose -p birja-prod ps`, `ufw status`, cert file modes and `/var/lib/birja/deploys.log`. I did not read any secrets.

The baseline is solid. Every script uses `set -Eeuo pipefail` (smoke-prod deliberately does not), variables are quoted, deploys hold a lock, migrations run before the backend swap, XFF is overwritten rather than appended, real_ip is trusted only from Cloudflare ranges, Postgres/Redis sit on an internal network, only `127.0.0.1:18000` is published, `server_tokens` is off, and the security headers are re-included in every location that uses `add_header`.

The main defects:
- **Rollback picks the wrong target.** After a failed deploy it goes two versions back, and a second rollback re-deploys the bad release. On the live host it is currently a no-op, because the last two log lines have the same SHA.
- **The Birja server block is the implicit 443 default server.** Any Host or SNI that reaches the origin gets the Birja app. Verified live.
- **One renew-cert path is broken.** When `start` finds cached authorizations, it tells the operator to run `finish`, which then always fails.
- **Two smoke checks can pass when they should fail.**

The accepted risk T-02.1-13a (Postgres superuser/no SSL until Phase 6) is not re-flagged.

## Critical Issues

### CR-01: `--rollback` targets the second-to-last log line, which is wrong after a failed deploy and after a rollback

**File:** `deploy/deploy.sh:171-198` (also `record` at 115-120)
**Issue:** `do_rollback` always uses `tail -n 2 | head -n 1`, the second-to-last line of `deploys.log`. Only successful runs are recorded, and rollbacks are recorded too. The result is wrong in three common cases:

1. **Failed deploy, then rollback.** This is the path `on_err` tells the operator to take ("To roll back: ... --rollback"). Deploy N+1 fails after `dc up -d --wait backend` (e.g. frontend build, `install-nginx.sh` or `health_check` fails). The new backend is live and the schema is migrated, but nothing is logged. The last good deploy is log[-1] = N, yet rollback checks out log[-2] = N-1. That runs code two releases old against a schema two migrations newer, which is the riskiest possible target.
2. **Rollback twice.** Log `[A, B, rollback(A)]` gives log[-2] = B, so the second "rollback" re-deploys the bad release B.
3. **Same SHA re-deployed.** This is the live state now: the last two lines are both `11a0161… main` (19:53:11 and 19:53:52). `--rollback` would redeploy the same SHA, a silent no-op that still reports success.

**Fix:** Pick the newest log entry whose SHA differs from the code actually serving now, and skip `rollback` entries, or keep an explicit "previous good" pointer:
```bash
current_sha=$(tail -n 1 "$DEPLOY_LOG" | awk '{print $2}')
# if HEAD != last recorded sha, a deploy failed mid-way: the last good one IS the log tail
if [ "$(git -C "$APP_DIR" rev-parse HEAD)" != "$current_sha" ]; then
  line=$(tail -n 1 "$DEPLOY_LOG")
else
  line=$(awk -v cur="$current_sha" '$4!="rollback" && $2!=cur' "$DEPLOY_LOG" | tail -n 1)
fi
[ -n "$line" ] || { echo "no earlier distinct deploy to roll back to" >&2; exit 1; }
```
Print the target SHA and require confirmation (or `--yes`) before acting. Add a test that runs a failed deploy followed by a rollback, and one that runs a double rollback.

## Warnings

### WR-01: Birja is the implicit `default_server` for :443, so any Host/SNI that reaches the origin gets the Birja app

**File:** `deploy/nginx/birja.nist.one.conf:14-17` (and `install-nginx.sh:57-62`)
**Issue:** Neither 443 server block has `default_server`. nginx uses the first one it loads, and `sites-enabled/birja.nist.one` sorts before `default` and `nist.one`. Verified on the host: `curl -k --resolve evil.example:443:127.0.0.1 https://evil.example/` returns the Birja SPA, and `/api/v1/health` returns 200. ufw allows all Cloudflare ranges, and those are shared by every Cloudflare customer. Anyone can therefore create their own Cloudflare zone, point it at 151.243.171.52 with SSL mode "Full" (non-strict), and serve the real Birja frontend and API under their own domain. That domain receives the session cookies, and its operator controls the edge (Workers), which makes credible phishing and session theft possible. Installing Birja also silently changed the unknown-SNI behavior of the pre-existing nist.one setup (D-01 says nist.one stays untouched).
**Fix:** Add an explicit catch-all 443 server that is installed with the Birja config and sorts first, e.g. `/etc/nginx/conf.d/birja-00-default-tls.conf` or a `sites-available/000-default-tls`:
```nginx
server {
    listen 443 ssl default_server;
    listen [::]:443 ssl default_server;
    server_name _;
    ssl_reject_handshake on;   # nginx >= 1.19.4; host has 1.24.0
}
```
Add a smoke check that a bogus SNI/Host to 127.0.0.1:443 is rejected.

### WR-02: renew-cert `start` tells you to run `finish` when no challenge is needed, but `finish` then always fails

**File:** `deploy/renew-cert.sh:268-272, 332-333`
**Issue:** If Let's Encrypt still holds valid authorizations (they are reused for about 30 days, e.g. after an early renewal or a retry), acme.sh issues the cert straight away. `start` then prints "run 'finish' directly" and exits 0 without writing `$PENDING`. `finish` calls `cmd_check`, `doh_check` sees no `$PENDING` and returns 1, so `finish` exits with "TXT record(s) not visible yet; not finishing". The key chmod and the expiry printout never run. This path has never been exercised: the RUNBOOK notes the first LE cert was installed directly with `--install-cert` and no pending file.
**Fix:** In `cmd_finish`, when `$PENDING` is missing, skip the DoH check and the second `--renew`, and go straight to `--install-cert`. Or make `start` do the install itself in the "Cert success" branch:
```bash
cmd_finish() {
    if [ -f "$PENDING" ]; then
        cmd_check || { echo "TXT record(s) not visible yet; not finishing" >&2; exit 1; }
        "$ACME" --renew ... || { ...; exit 1; }
    fi
    install -d -m 750 "$OUT_DIR"
    "$ACME" --install-cert ...
```

### WR-03: Deploy swaps the backend before building the frontend and installing nginx, so failures leave a mixed state

**File:** `deploy/deploy.sh:154-165`
**Issue:** The order is: migrate, start the new backend, build the frontend, install nginx, health check. The frontend build (`npm ci` downloads from the network) and `install-nginx.sh` (`nginx -t` can fail) are the steps most likely to fail. When they do, prod runs the new backend and schema with the old frontend, the deploy is not recorded, and CR-01 makes the advised rollback go to the wrong version. The RUNBOOK (line 39) even describes the opposite order ("builds the frontend ... runs migrations, switches").
**Fix:** Do all fallible preparation before anything goes live: `build backend`, then build the frontend into `releases/<sha>-<ts>` without swapping, then `check-nginx-config.sh`. Only after that run migrate, `up -d --wait backend`, `swap_current`, `install-nginx.sh` and `health_check`. Split `build_frontend_release` into build and swap.

### WR-04: Smoke check "placeholder secret refused" passes on any failure

**File:** `deploy/smoke-prod.sh:197-203`
**Issue:** Any non-zero exit of `docker compose run ...` counts as PASS. Possible causes include a missing image, a compose interpolation error, an unreadable env file, the Docker daemon being down, or an import error in `app.core.config`. Output is sent to `/dev/null`, so the check cannot tell "Settings rejected the placeholder" apart from "nothing ran".
**Fix:** Assert the specific rejection and add a positive control:
```bash
out=$(docker compose ... run --rm --no-deps -e OTP_HMAC_SECRET=change-me-... backend \
  python -c "from app.core.config import Settings; Settings()" 2>&1)
if printf '%s' "$out" | grep -q 'ValidationError' && printf '%s' "$out" | grep -qi 'otp_hmac_secret'; then pass ...; else fail ...; fi
```
Print only the matched class name, never `$out`. Optionally first confirm that the same command without the override exits 0.

### WR-05: Public smoke check "openapi.json not exposed" cannot fail

**File:** `deploy/smoke-prod.sh:113-117`
**Issue:** nginx proxies only `/api/`. `https://$H/openapi.json` falls through to `location /`, where `try_files $uri /index.html` returns the SPA HTML, so `grep '"openapi"'` never matches. The check would pass even with `ENV=dev` and the docs enabled. The local check 6 hits the app directly, but `--public` is documented as standalone ("no host access needed").
**Fix:** Probe paths that actually reach the app through nginx and assert a non-200, e.g. `/api/v1/openapi.json`, `/api/v1/docs`, `/api/openapi.json`. Better still, compare the backend's actual `openapi_url`: `curl -s https://$H/api/v1/health` plus a negative check that `https://$H/docs` returns the SPA (`id="root"`) and not Swagger (`swagger-ui`).

### WR-06: The frontend build runs `npm ci` as root with lifecycle scripts, writing to a bind-mounted prod checkout

**File:** `deploy/deploy.sh:96`
**Issue:** `docker run --rm -v "$APP_DIR/frontend":/app ... npm ci && npm run build` runs as root in the container, with network access. Any dependency's install script can write as host root anywhere under `/srv/birja/frontend` (including tracked files, `node_modules/.bin`, and `dist` which is then published to `/var/www`). `deploy.sh` and `install-nginx.sh` from the same tree then run as host root. A compromised transitive npm package therefore becomes a host-root foothold on a box serving the public site.
**Fix:** Run as an unprivileged UID and disable install scripts where possible:
```bash
docker run --rm --user 1000:1000 -e HOME=/tmp -e npm_config_cache=/tmp/.npm \
  -v "$APP_DIR/frontend":/app -w /app "$NODE_IMAGE" sh -c 'npm ci --ignore-scripts && npm run build'
```
Give the frontend directory matching ownership, or build into a copy, and only `cp` the `dist/` output into the release as root.

### WR-07: Rollback does not restore the nginx config, and redeploys can't be told apart in the log

**File:** `deploy/deploy.sh:182-198`
**Issue:** Rollback checks out the old SHA and rebuilds the backend, but never re-runs `install-nginx.sh`. The newer nginx config (CSP, proxy snippet, rate limits) stays live even when the rolled-back frontend needs the older one, e.g. a CSP change made for a new asset origin. `health_check` only greps `id="root"`, which every release contains, so it cannot detect the mismatch.
**Fix:** Run `"$APP_DIR/deploy/install-nginx.sh"` in `do_rollback` after the checkout, the same as in `do_deploy`. Have `health_check` confirm the served `index.html` belongs to `$RELEASE_DIR`, e.g. `cmp` the fetched index against `$RELEASE_DIR/index.html`.

## Info

### IN-01: A `DEPLOY_REF` containing whitespace corrupts the deploy log

**File:** `deploy/deploy.sh:118-119, 180-181`
**Issue:** The log is space-separated and parsed with `awk '{print $2/$3}'`. A ref with spaces (or a newline) shifts the fields.
**Fix:** Validate `REF` against `^[A-Za-z0-9._/-]+$` in `main`, or write a TAB-separated log.

### IN-02: RUNBOOK's deploy description doesn't match the script

**File:** `deploy/RUNBOOK.md:39`
**Issue:** It says "builds the frontend into a new release, starts the stack, runs migrations". The actual order is migrate, start the backend, then build the frontend (see WR-03).
**Fix:** Update the text once the order is settled.

### IN-03: Prod containers lack basic hardening; the Redis password is in the container Cmd

**File:** `docker-compose.prod.yml:140-229`
**Issue:** There is no `cap_drop: [ALL]`, `read_only: true` or `tmpfs` on the backend. `--requirepass ${REDIS_PASSWORD}` is baked into the container `Config.Cmd`, readable by anyone in the `docker` group via `docker inspect`. Redis hides it from `ps`; I checked, and the host process list has 0 matches.
**Fix:** Add `cap_drop: [ALL]` and `read_only: true` with a `/tmp` tmpfs to the backend. Pass the Redis password via a mounted config or ACL file, or with `sh -c 'exec redis-server --requirepass "$REDIS_PASSWORD" ...'`. That last form keeps it out of `inspect` Cmd but leaves it in Env.

### IN-04: `--forwarded-allow-ips` trusts the whole /24, and local users can spoof XFF

**File:** `docker-compose.prod.yml:216-218`
**Issue:** Through docker-proxy, every connection to `127.0.0.1:18000` arrives from the gateway `172.29.50.1`. Any local process or user on the host can therefore reach the backend directly with an arbitrary `X-Forwarded-For` and pick its own rate-limit bucket.
**Fix:** Narrow the setting to `172.29.50.1`. If the host ever gets other users, consider a Unix socket or a host firewall rule on 18000.

### IN-05: Some useful security headers are missing

**File:** `deploy/nginx/snippets/birja-security-headers.conf`
**Issue:** There is no `Permissions-Policy` (e.g. `camera=(), microphone=(), geolocation=()`) and no `Cross-Origin-Opener-Policy: same-origin`.
**Fix:** Add both with `always`.

### IN-06: Smoke checks that are weaker than their labels say

**File:** `deploy/smoke-prod.sh:100-105, 217, 247-249`
**Issue:**
- The public "valid chain" check validates Cloudflare's edge cert, not the origin.
- `ss -ltnH` checks TCP only, not UDP listeners.
- `LOOP=1` can come from a previous run's key that is still inside the TTL window, so it does not prove this request reached the rate limiter.
**Fix:** Rename the label. Add `ss -lunH`. Delete `sim:rl:ver:ip:127.0.0.1` before the probe, or compare TTL/counter before and after.

### IN-07: `test_env_required` uses a loose assertion

**File:** `backend/tests/test_config.py:158-163`
**Issue:** `"env" in str(exc).lower()` would also match unrelated messages.
**Fix:** `assert any(e["loc"] == ("env",) and e["type"] == "missing" for e in exc_info.value.errors())`.

### IN-08: `cloudflare-ips.sh` treats unknown arguments as a full write and reload

**File:** `deploy/cloudflare-ips.sh:92-93, 159-169`
**Issue:** A typo such as `--check-uf` or `--prin` falls through to rewriting the snippet and reloading nginx.
**Fix:** Parse the arguments with a `case` that rejects anything unknown and exits 2.

### IN-09: `init-prod-env.sh` leaves a temp file behind on failure

**File:** `deploy/init-prod-env.sh:235-259`
**Issue:** If anything fails between `mktemp` and `mv`, a partial secrets file (mode 600, root) stays in `/etc/birja`.
**Fix:** `trap 'rm -f "$tmp"' EXIT` after `mktemp`, and clear it after the `mv`.

### IN-10: The CSP spec covers only the login page

**File:** `frontend/e2e/csp.spec.ts:12-40`
**Issue:** It never visits pages behind sign-in, so runtime inline styles or new connect targets on later pages (portfolio, trade) are not checked against the CSP.
**Fix:** Extend it when those pages ship, e.g. with a pre-seeded session on a staging account.
